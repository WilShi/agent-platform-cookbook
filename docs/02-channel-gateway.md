# 02 · 渠道接入网关：消息路由、会话映射与降级

> 解决的问题：同一个智能体平台要同时服务飞书、企微、钉钉、微信等多个渠道，每个渠道的消息模型、鉴权方式、限流规则都不同。

## 核心模式：Channel Gateway

```
飞书 ──┐                          ┌── 会话 A（平台视角的同一个用户）
企微 ──┼── 渠道适配 ──► 消息总线 ──┤
钉钉 ──┤    （入站归一化）           └── 会话 B
微信 ──┘
```

**要点：**

1. **入站归一化**：每个渠道适配器把渠道消息（卡片、富文本、@提及、引用）转成平台标准消息对象；出站时反向渲染成渠道原生格式。**渠道特性只活在适配器里**。
2. **会话映射**：同一个用户在飞书私聊和企微群里是两个渠道会话，但平台侧可能映射为同一身份。身份解析层（Identity Resolver）负责"渠道身份 → 平台用户"的归并，且必须支持一个用户多渠道并行会话的隔离。
3. **限流与降级**：渠道都有发送频率限制（飞书尤其明显）。网关需要：出站队列 + 每渠道独立限速器 + 降级策略（长文本转文件/合并发送/分段）。
4. **幂等与重试**：渠道回调会重复推送（飞书重试、企微超时重推），入站必须以事件 id 幂等去重；出站失败按渠道特性重试（指数退避，尊重渠道限流信号）。

## 踩坑记录（脱敏）

- **token 刷新竞态**：多渠道共用一个 token 缓存时，并发刷新会互相踩踏（同时发起多次刷新请求，旧 token 被覆盖）。加分布式锁或单例刷新器。
- **富文本降级**：Markdown 表格在部分渠道渲染失败——出站渲染器要有降级链（表格 → 列表 → 纯文本）。
- **大消息拆分**：渠道单条消息有长度上限，超长回复要在语义边界（段落）拆分，而不是按字符硬切。

## 最小落地清单

- [ ] 渠道适配器接口（入站归一化 + 出站渲染）
- [ ] 身份解析与会话映射表
- [ ] 出站队列 + 每渠道限速器
- [ ] 事件幂等去重（event id）
- [ ] 降级链（富文本 → 纯文本 → 文件）
