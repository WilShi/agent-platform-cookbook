# 01 · 多框架统一纳管：适配层、能力探测与版本兼容

> 解决的问题：企业里同时存在多套智能体框架（OpenClaw、ZeroClaw、DeepSeek Harness……），业务方想随时切换/并存，平台侧不能为每个框架重写一遍接入。

## 核心模式：Adapter + Capability Probe

```
业务调用方
    │  统一协议（平台自有契约）
    ▼
┌─────────────────────────────────────┐
│  Gateway 适配层（Adapter Registry）   │
│  ┌─────────┐ ┌─────────┐ ┌────────┐ │
│  │ OpenClaw│ │ ZeroClaw│ │  DSH   │ │
│  │ Adapter │ │ Adapter │ │ Adapter│ │
│  └─────────┘ └─────────┘ └────────┘ │
└─────────────────────────────────────┘
    │            │            │
  OpenClaw    ZeroClaw       DSH
```

**要点：**

1. **契约先行**：平台先定义自己的统一调用契约（会话、消息、工具结果、流式事件），任何框架 adapter 只做"框架协议 → 平台契约"的单向翻译，绝不允许框架概念泄漏到上层。
2. **能力探测（Capability Probe）**：接入一个新框架时，先跑探测清单——支持哪些通道（streaming？工具调用？多模态？）、会话模型（有状态/无状态）、错误语义。探测结果写入能力注册表，路由层按能力分流。
3. **版本兼容策略**：按"能力声明"而非"版本号白名单"做兼容——框架升级后先跑探测，能力变了再动 adapter。参考 DSH 0.2.x 引入的 `engines.dsh` 声明机制：让框架自己声明兼容范围。

## 踩坑记录（脱敏）

- **不要把框架的会话 id 直接当平台会话 id**：框架重启/升级后 id 语义会变。平台自建会话映射表，框架 id 只作外键。
- **流式输出的背压**：某框架流式吐字远快于渠道消费能力时，适配层要做缓冲+节流，否则渠道侧丢消息。
- **错误语义对齐**：框架 A 的"超时"、框架 B 的"限流"、框架 C 的"上下文溢出"必须映射到平台统一的错误码，否则上层的重试和降级策略没法写。

## 最小落地清单

- [ ] 统一调用契约（会话/消息/事件/错误码）
- [ ] Adapter 接口 + 注册表
- [ ] 能力探测清单（每个新框架接入必跑）
- [ ] 会话映射表（平台 id ↔ 框架 id）
- [ ] 错误码对齐表
